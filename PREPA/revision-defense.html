1Phrases incontournables

Les réponses que le prof va presque sûrement entendre. À mémoriser mot pour mot.
A/B testing
Nginx reçoit la requête sur /test, son upstream liste mes deux apps, et il répartit en round-robin : une fois Spring Boot (version A), une fois Django (version B).
Multi-stage (Spring)
Premier FROM = grosse image Maven + JDK pour compiler le .jar. Deuxième FROM = petite image JRE pour l'exécuter. Je copie seulement le .jar avec COPY --from=build. Ça optimise les ressources. C'est l'exercice 4 du TD 03.
Un seul FROM (Django)
Python est interprété : pas de compilation, donc pas besoin d'image de build, un seul FROM suffit.
depends_on
Garantit l'ordre de démarrage, pas que l'app soit prête à répondre. Pour la disponibilité réelle il faudrait un healthcheck (TD 04).
Slash de proxy_pass
Le / final fait que nginx remplace /test par /, donc le backend reçoit sa racine. Sans le slash, il recevrait /test qu'il ne connaît pas → 404.
EXPOSE
Purement documentaire. Le vrai mapping de port, c'est ports: dans le compose. Commenter EXPOSE ne casse rien (TD 03 p.8).
Managed Identity
Mes App Services pull l'image depuis l'ACR via la Managed Identity + le rôle AcrPull, sans aucun secret. C'est le pattern du TD 09.
Service Principal
Un compte robot Azure pour le pipeline. Ses 4 valeurs (ARM_CLIENT_ID / SECRET / TENANT_ID / SUBSCRIPTION_ID) sont des variables masquées dans GitLab.
Docker dans le pipeline
Mon runner monte /var/run/docker.sock, donc mes jobs docker build/push parlent au démon Docker de l'hôte. C'est la technique « accès au démon hôte » du TD 07. PAS du Docker-in-Docker.
SNI (P6)
Azure mutualise des milliers d'apps sur les mêmes IPs. Sans SNI, nginx ne dit pas à quel domaine il veut parler pendant le handshake TLS, et la connexion échoue. D'où proxy_ssl_server_name on.
PORT vs WEBSITES_PORT
Le TD 08 dit explicitement d'utiliser PORT (et non WEBSITES_PORT). Je l'ai suivi, et mes apps répondent sur leurs URLs Azure.

6Docker & Dockerfiles — P1

LE COURS

Le vocabulaire (mots exacts du TD 03)

  • Image : un modèle qui contient tout ce dont l'app a besoin pour s'exécuter (code, libs, dépendances). (TD 03 p.2)
  • Conteneur : une instance en cours d'exécution d'une image. (p.3)
  • Dockerfile : un fichier texte d'instructions pour construire une image. (p.6)

Dockerfile Spring = multi-stage (deux FROM)

C'est l'exercice 4 du TD 03. Idée : compiler dans une grosse image, exécuter dans une petite.

  • 1er FROM (maven:...) : a Maven + le JDK → compile le .jar. = "l'image pour la compilation".
  • 2e FROM (...jre-alpine) : juste la JRE → exécute. = "l'image pour l'exécution", c'est elle l'image finale.
  • Entre les deux : COPY --from=build copie SEULEMENT le .jar.
À dire : « 1ère image = compiler, 2e image = exécuter. Je copie juste le .jar. L'image finale est légère, sans les outils de build. Ça optimise les ressources. »

Dockerfile Django = un seul FROM

Python est interprété : pas de compilation, donc pas besoin d'image de build. Juste l'interpréteur + les dépendances + le code.

Mémo : Java compilé → multi-stage. Python interprété → un seul FROM.

Les directives (toutes du TD 03 p.6-7)

FROM (image de base), WORKDIR (dossier courant), COPY (ajoute des fichiers), RUN (exécute pendant le build), LABEL (métadonnée = mon matricule), EXPOSE (documente un port), CMD (commande au démarrage).

EXPOSE est purement documentaire : il n'ouvre rien. Le vrai mapping, c'est ports: dans le compose (TD 03 p.8).
Pourquoi deux FROM dans le Dockerfile Spring ?
Multi-stage build (TD 03 ex.4). Le 1er FROM (Maven+JDK) compile le .jar ; le 2e (JRE alpine) l'exécute. On copie juste le .jar entre les deux. L'image finale est légère et plus sûre (pas d'outils de build).
Codespring-boot/Dockerfile
À dire« 1ère image = compiler, 2e image = exécuter. Je copie le .jar avec COPY --from=build. Ça optimise les ressources. »
Pourquoi -DskipTests dans le build de l'image ?
Pour ne pas jouer les tests pendant la construction de l'image : ils tournent dans le pipeline CI (Partie 3). Ça accélère le build et évite de les jouer deux fois.
À dire« Je saute les tests ici, ils sont dans le pipeline P3. »
Pourquoi le Dockerfile Django n'a qu'un seul FROM ?
Python est interprété, il n'y a pas d'étape de compilation. J'ai juste besoin de l'interpréteur + les dépendances + le code. Un multi-stage n'apporterait rien.
Codedjango/Dockerfile
À dire« Java compilé → multi-stage. Python interprété → un seul FROM. »
À quoi sert LABEL author="66045" ?
C'est une métadonnée de l'image (mon matricule = signature). Visible via docker inspect. Le TD 03 p.7 le montre avec LABEL author="g12345".
À dire« Ma signature dans l'image, visible avec docker inspect. »

7Docker Compose

LE COURS

Le docker-compose.yml lance mes 3 conteneurs d'un coup et les met sur un réseau commun. C'est ce que fait docker compose up.

Les clés (toutes définies TD 04 p.11)

  • services : mes 3 conteneurs.
  • build: ./spring-boot : construit l'image depuis ce Dockerfile.
  • container_name : nom fixe du conteneur.
  • ports: "8080:8080" : mapping hôte → conteneur.
  • networks : rattache au réseau partagé ab-network.
  • depends_on : ordre de démarrage.

Le réseau bridge + DNS interne

Grâce au réseau ab-network (driver bridge), nginx joint spring-boot et django par leur nom — c'est le DNS interne de Docker. Sans réseau commun, nginx ne pourrait pas les résoudre.

depends_on : LA nuance (Question 4)

Il garantit l'ORDRE de démarrage (nginx après les apps), MAIS pas que l'app soit PRÊTE à répondre — juste que son conteneur est lancé.

Démarré ≠ prêt : au démarrage on peut avoir un 502, le temps que Spring finisse de booter (~10-30 s). Le conteneur est lancé, mais Spring n'écoute pas encore. Pour la vraie disponibilité : un healthcheck (TD 04 p.11, mot pour mot).
Mots-clés fixes (services, ports, depends_on…) = le langage compose, pas renommables. Noms que j'ai choisis (spring-boot, ab-network) = renommables, mais à répercuter partout (ex. l'upstream nginx).
Comment nginx trouve-t-il spring-boot et django ?
Via le DNS interne du réseau Docker partagé ab-network. Les conteneurs sur le même réseau bridge se joignent par leur nom de service. Sans réseau commun, nginx ne pourrait pas les résoudre.
Codedocker-compose.yml + nginx.conf (server spring-boot:8080)
À dire« Le DNS interne de Docker résout les noms de services sur le réseau bridge partagé. »
C'est quoi driver: bridge ?
Le driver réseau par défaut. Les conteneurs connectés se parlent entre eux, mais ne sont pas accessibles de l'extérieur sauf via les ports explicitement mappés (TD 04 p.12).
À dire« Réseau virtuel isolé ; communication interne, accès externe seulement via les ports mappés. »
Quels mots peux-tu renommer dans le compose ?
Les mots-clés (services, build, ports, depends_on, networks, driver…) sont fixes — c'est le langage docker-compose (listés TD 04 p.11). Les noms que j'ai choisis (services spring-boot/django/nginx, le réseau ab-network) sont renommables, mais il faut répercuter partout (ex. l'upstream nginx).
À dire« Mot-clé = fixe. Nom que j'ai inventé = renommable, mais je dois changer toutes ses références. »

8Nginx local — P2

LE COURS

Nginx est le reverse proxy qui fait l'A/B testing — celui que tu vois alterner Spring/Django quand tu rafraîchis localhost/test.

upstream + round-robin

L'upstream apps-ab liste mes 2 apps. Quand un upstream a plusieurs server, nginx ALTERNE par défaut : requête 1 → Spring, requête 2 → Django… C'est ça l'A/B, rien de codé en plus.

"round-robin" n'est pas écrit dans le TD 05 (le comportement y est montré) ; il est dans mon commentaire de code. Je peux dire "nginx alterne entre les serveurs".

Le slash de proxy_pass (LE détail)

Il y a 2 sauts : (1) toi → nginx (localhost/test), (2) nginx → backend.

  • AVEC le slash (proxy_pass http://apps-ab/) : nginx remplace /test par / → le backend reçoit sa racine → la page existe.
  • SANS le slash : le backend reçoit /test → 404 (mes apps n'ont pas de route /test).

La substitution est automatique (nginx), déclenchée par le slash. location /test = ce qui est remplacé ; le chemin du proxy_pass = par quoi.

2 décisions par requête : le chemin (toujours /, via le slash) + le serveur:port (8080 ou 8000, via le round-robin). nginx envoie à spring-boot:8080/ OU django:8000/, en alternance. Le / est constant, le port alterne — c'est ça l'A/B.
Nginx fait un reverse proxy, pas une "redirection" HTTP (ton URL reste localhost/test). Dire "il route / proxifie vers", pas "il redirige". Et /test est imposé par la consigne P2.
Comment se fait le round-robin / l'A/B ?
Quand un upstream a plusieurs server, nginx alterne par défaut : requête 1 → Spring, requête 2 → Django, etc. Rien de codé en plus.
Codenginx/nginx.conf (upstream apps-ab)
À dire« Comportement par défaut de l'upstream. Le mot "round-robin" n'est pas dans le TD mais le comportement y est montré ; je peux dire "nginx alterne entre les serveurs". »
Le rôle du slash final de proxy_pass
Avec proxy_pass http://apps-ab/ (slash), nginx remplace /test par / → le backend reçoit sa racine. Sans le slash, il reçoit /test → 404. La substitution est automatique : nginx remplace ce que matche le location par le chemin du proxy_pass.
Codenginx/nginx.conf (location /test)
À dire« Le slash fait que nginx remplace /test par /. Mes apps répondent sur /, pas sur /test. Sans le slash → 404. »
Anecdote : l'underscore (400 Bad Request)
Au début l'upstream s'appelait apps_ab avec underscore → 400. Nginx met le nom de l'upstream dans le header Host, et Tomcat refuse les underscores (RFC). Renommé apps-ab → réglé.
À direMontre que j'ai débogué du vrai. « Underscore interdit dans un nom d'hôte, j'ai mis un tiret. »
Pourquoi un Dockerfile nginx et pas un volume (comme le TD) ?
Le TD 05 monte la conf en volume, mais la consigne P2 demande explicitement « créer un Dockerfile Nginx personnalisé ». La consigne prime.
À dire« La consigne P2 exige un Dockerfile nginx perso. »

9Pipeline — P3 & P5

LE COURS

Tag ≠ pipeline (important)

  • Tag = marqueur git posé sur un commit. J'en ai 6, un par partie. Ils prouvent que les 6 parties sont livrées. C'est ce que le prof récupère.
  • Pipeline = l'exécution automatique du CI/CD déclenchée à chaque push. Il enchaîne des jobs.

Le vocabulaire (TD 07)

  • Stage : une étape (séquentielles).
  • Job : une tâche dans un stage.
  • Runner : le conteneur Docker chez moi qui exécute les jobs.

Mon fichier : 4 stages, 8 jobs

build   -+
test    -+  Partie 3 (CI : compiler + tester)
deploy  -+
update  -+  Partie 5 (déployer sur Azure)

P3 — build & test

build-spring (image maven, mvn compile), build-django (image python, pip install). Puis test-spring (mvn test), test-django (manage.py test). Chaque job précise son image: (l'environnement) et son stage:. build doit réussir avant test.

P5 — deploy & update

deploy (image docker:latest) : docker login à l'ACR avec le Service Principal (--password, forme consigne), puis docker build + docker push.

Technique = accès au démon HÔTE via docker.sock (monté dans le runner), PAS dind. Mon fichier n'a PAS de services: docker:dind. Ne jamais dire "dind" → dire "accès au démon hôte" (TD 07 p.20-22).

update (image azure-cli) : az login --service-principal puis az webapp restart → l'App Service re-pull l'image fraîche.

Le runner

Un conteneur Docker chez moi, enregistré au projet via un token. Pour chaque job il lance un conteneur frais de l'image du job. Enregistré avec --docker-volumes /var/run/docker.sock pour que les jobs deploy parlent au démon Docker de l'hôte.

Vocabulaire : pipeline, stage, job, runner, tag
Pipeline = processus auto déclenché au push. Stage = étape (séquentielles). Job = tâche dans un stage. Runner = le conteneur Docker chez moi qui exécute les jobs. Tag = marqueur git (j'en ai 6, un par partie) — différent du pipeline.

11Nginx Azure — P6

LE COURS

Un 2e nginx, séparé du premier. Même principe (router /test en A/B), mais vers mes apps Azure (URLs publiques HTTPS) au lieu des conteneurs locaux. Le Dockerfile est identique à celui de la P2 ; la différence est dans le nginx.conf.

Les différences avec la P2

  • Cible : URLs Azure (app-spring-66045.azurewebsites.net:443) au lieu de conteneurs locaux.
  • Protocole : proxy_pass https:// (pas http) ; port 443.
  • SSL : proxy_ssl_server_name on + proxy_ssl_name $proxy_host.

Le SNI (mon apport — pas vu en cours)

Azure App Service mutualise des milliers d'apps sur les mêmes IPs publiques. Pendant le handshake TLS, nginx doit indiquer le nom de domaine — c'est le SNI (Server Name Indication) — sinon Azure ne sait pas quel certificat/app servir et la connexion échoue. proxy_ssl_server_name on active l'envoi du SNI.

Le SNI est ABSENT du TD 05 et du TD 08. À NE PAS sortir de moi-même. Si on me pousse : justifier par la mutualisation des IPs Azure + le TD 05 qui invite à consulter la doc pour le HTTPS.

Honnêteté (le Host header)

Avec un upstream multi-serveurs, le Host header par défaut est le nom de l'upstream, qu'Azure ne reconnaît pas. Mon A/B marche en local ; pour Azure la gestion fine du Host header serait à affiner. Alternative native : Azure Front Door (note de la consigne P6).

13Cours bête (basiques)

Image vs conteneur ?
Une image est un modèle qui contient tout ce dont l'app a besoin (TD 03 p.2). Un conteneur est une instance en cours d'exécution d'une image (TD 03 p.3).
C'est quoi un Dockerfile ?
Un fichier texte qui contient une série d'instructions pour construire une image (TD 03 p.6).
ENTRYPOINT vs CMD ?
ENTRYPOINT = le programme principal qui s'exécute toujours. CMD = des arguments par défaut, remplaçables si on en passe à docker run (TD 04 p.4). Mes Dockerfiles utilisent CMD.
Stages séquentiels ou parallèles ?
Les stages s'exécutent en séquence ; les jobs d'un même stage en parallèle (si plusieurs runners). TD 07 p.10-12.
Pourquoi des images alpine ?
Alpine = distribution Linux minimale → images légères. C'est une bonne pratique d'optimisation de la taille (TD 04 p.5).
