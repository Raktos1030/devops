Échelle 1 — vue d'ensemble

C'est quoi ce projet, en 90 secondes

Un test A/B, c'est quand tu as deux versions de la même page et que tu envoies la moitié des visiteurs sur la version A, l'autre moitié sur la version B — pour comparer laquelle marche le mieux.

Ici, les deux versions sont deux applications web qui affichent quasiment la même chose :

Version A
Spring Boot · Java 21
écoute sur le port 8080
Version B
Django · Python 3.12
écoute sur le port 8000

L'une affiche « Version SPRING BOOT », l'autre « Version DJANGO ». C'est volontairement nul comme contenu : ce sont des cobayes. Ce qui est évalué, ce n'est pas les applis.

Ce que TU as fait (et ce que tu n'as pas fait)

Le code des deux applis, c'est l'école qui te l'a donné. Ton travail, c'est tout ce qui les entoure — la chaîne qui va de « du code sur mon disque » à « une appli qui tourne sur Internet » :

  1. Les mettre en boîte — Docker : chaque appli devient une image autonome qui contient son langage, ses dépendances et son code.
  2. Les faire tourner ensemble — Docker Compose : une commande, trois conteneurs démarrent.
  3. Mettre un aiguilleur devant — Nginx : c'est lui qui alterne A / B. C'est le cœur de la démo.
  4. Automatiser — GitLab CI : à chaque git push, ça compile, ça teste, ça fabrique les images et ça les livre. Sans toi.
  5. Créer les serveurs en code — Terraform : au lieu de cliquer dans le portail Azure, tu décris l'infra dans des fichiers, et une commande la crée.

Ces cinq points sont exactement les cinq gros sujets du cours DevOps. Le projet n'est rien d'autre qu'un prétexte pour les enchaîner.

Si le prof dit « présente-moi ton projet »

« J'ai deux versions d'une même application web fournies par l'école — une en Spring Boot, une en Django. Mon travail c'est toute la chaîne autour : je les ai conteneurisées avec Docker, orchestrées avec Docker Compose, mis un Nginx devant qui fait l'A/B testing en round-robin sur la route /test, automatisé la compilation, les tests et le déploiement dans un pipeline GitLab CI, et décrit l'infrastructure Azure en Terraform. Le tout découpé en six parties, une par tag Git. »

Le mot « DevOps », si on te le demande. C'est la culture qui consiste à supprimer le mur entre ceux qui écrivent le code (Dev) et ceux qui le font tourner en production (Ops), en automatisant tout ce qu'il y a entre les deux. Ton projet, c'est littéralement cette automatisation : personne ne copie un fichier à la main nulle part.

Échelle 3 — le mécanisme

Comment ça marche, concrètement

Il y a deux mondes dans ce projet, et c'est le piège numéro un des débutants : ne les mélange pas. Le monde local (ta machine) et le monde Azure (Internet). Chacun a son Nginx.

Monde 1 — en local, sur ta machine

Tu tapes docker compose up --build et trois conteneurs démarrent. Tu ouvres http://localhost/test, tu rafraîchis : ça affiche A, puis B, puis A, puis B.

Ton navigateurhttp://localhost/test

▼                         ▼
app-spring-bootspring-boot:8080Version A

les 3 conteneurs sont sur le réseau Docker ab-network (driver bridge)

Ce qui fait l'alternance, c'est le round-robin : le comportement par défaut de Nginx quand on lui donne une liste de serveurs. Requête 1 → le premier, requête 2 → le deuxième, requête 3 → le premier… Tu n'as codé aucun tirage au sort.

Ce qui permet à Nginx de trouver les applis, c'est le réseau Docker partagé. Dans un réseau Docker, un conteneur peut en joindre un autre par son nom de service : Docker fournit un DNS interne. C'est pour ça que la config Nginx écrit server spring-boot:8080; et pas une adresse IP.

Piège classique

« Qu'est-ce qui fait le 50/50 ? »

Ne dis jamais « j'ai codé un randomiseur ». La réponse : « c'est le round-robin par défaut de la directive upstream de Nginx, je n'ai rien ajouté. Si je voulais du pondéré, j'écrirais server X weight=70;. »

Le vocabulaire Azure minimum

Resource Group
Un dossier logique qui contient toutes tes ressources Azure. Le supprimer supprime tout d'un coup.
ACR
(Container Registry)
Ton dépôt d'images Docker privé, chez Azure. C'est le « Docker Hub » perso du projet.
App Service
Un serveur web géré par Azure. Tu lui dis « fais tourner cette image Docker », il s'occupe du reste (HTTPS, nom de domaine, redémarrages).
App Service Plan
La machine (et le tarif) sur laquelle tournent tes App Services. Tu en as un seul, en B1, partagé par les deux applis — pour ne pas payer deux fois.

Un compte robot Azure. Le pipeline ne peut pas taper un mot de passe dans un navigateur, donc il s'authentifie avec ça.

Un badge que porte l'App Service lui-même, sans mot de passe, pour aller chercher son image dans l'ACR.
La phrase qui montre que tu as compris

« Il y a deux identités différentes, exprès. Le pipeline tourne chez moi, donc il lui faut des identifiants : c'est le Service Principal, qui pousse les images. L'App Service tourne sur Azure, donc il peut utiliser une identité managée sans mot de passe, qui tire les images. Deux usages, deux identités, moindre privilège. »

Les 6 fichiers à connaître, classés par risque

Le prof peut pointer n'importe quelle ligne d'un fichier que tu as écrit et te demander de l'expliquer. Voici ces fichiers, du plus probable au moins probable. Si tu n'as le temps que pour trois, fais les trois premiers.

La règle de tri. Tout ce qui est dans spring-boot/src/, django/demo/, manage.py, pom.xml = code de l'école, tu n'as pas à le défendre (« c'est le code applicatif fourni, je n'y ai pas touché »). Tout le reste — Dockerfile, compose, nginx.conf, .gitlab-ci.yml, terraform — c'est toi.
1.gitlab-ci.yml

À la racine du dépôt · couvre 2 des 6 parties (P3 et P5) · c'est LE fichier DevOps du projet

C'est la recette que GitLab exécute automatiquement à chaque git push. Tout est dedans : quoi compiler, quoi tester, quoi déployer, dans quel ordre.

Le squelette

stages:
  - build      # P3 — compiler / installer les dépendances
  - test       # P3 — lancer les tests unitaires
  - deploy     # P5 — fabriquer les images et les pousser sur l'ACR
  - update     # P5 — redémarrer les App Services Azure

Trois mots à ne jamais confondre :

pipeline
L'exécution complète, déclenchée par un push. Un pipeline contient des stages.
stage
Une étape. Les stages s'exécutent l'un après l'autre, dans l'ordre déclaré. Si un stage échoue, les suivants sont annulés.
job
Une tâche concrète dans un stage. Les jobs d'un même stage peuvent tourner en parallèle (s'il y a assez de runners).

Si le prof demande « pourquoi update après deploy ? »

« Parce que si je redémarrais les App Services avant d'avoir poussé la nouvelle image, ils re-téléchargeraient l'ancienne. L'ordre des stages garantit que update ne tourne que si deploy a réussi. »

Le runner — la question qui tombe presque à coup sûr

GitLab ne fait pas tourner ton pipeline. Il se contente de dire « j'ai un job pour quelqu'un ». Celui qui l'exécute, c'est un runner : un programme que tu as enregistré toi-même auprès de GitLab, avec un token.

Chez toi, ce runner est un conteneur Docker qui tourne sur ta machine. Pour chaque job, il fait quatre choses : il démarre un conteneur neuf basé sur l'image: du job, il y clone le dépôt, il exécute le script:, puis il détruit le conteneur et renvoie les logs à GitLab.

La question à tiroir

« Comment un job qui tourne dans un conteneur peut-il lui-même faire docker build ? Il y a Docker dedans ? »

Non. À l'enregistrement du runner, tu as monté le socket Docker de la machine hôte dans le conteneur : -v /var/run/docker.sock:/var/run/docker.sock. Le client Docker du job envoie donc ses ordres au démon Docker de ta machine. L'alternative, c'est Docker-in-Docker (DinD), plus lourd à configurer. C'est la technique « accès au démon hôte » du TD 07.

Vérifie ce point sur ton dépôt. Dans tes derniers pipelines, les jobs de déploiement s'appellent push-images et update-apps — donc les deux jobs de chaque stage ont peut-être été fusionnés en un seul depuis. Ouvre ton vrai .gitlab-ci.yml et compte tes jobs : c'est ton fichier que le prof lira, pas celui-ci.

Un réseau Docker privé partagé par les trois conteneurs. C'est lui qui permet la résolution par nom de service. bridge est le driver par défaut : réseau virtuel isolé, l'extérieur n'entre que par les ports listés dans ports:.
Question quasi certaine

« À quoi sert depends_on exactement ? »

La réponse complète, celle qui rapporte des points : « depends_on garantit l'ordre de démarrage, mais pas que l'application soit prête à répondre. Docker considère le service démarré dès que le processus est lancé, même si Spring Boot met encore dix secondes à s'initialiser. Pour vraiment attendre, il faudrait un healthcheck sur les services. »

Le lien à voir entre les fichiers

« Change le port de Django de 8000 à 8050. »

C'est LE test de compréhension. Il y a trois endroits, et en oublier un casse tout : django/Dockerfile (le CMD … runserver 0.0.0.0:8050 et l'EXPOSE), docker-compose.yml (la ligne ports:), et nginx/nginx.conf (server django:8050;). Dis-le à voix haute avant de taper.

3nginx/nginx.conf

Dossier nginx/ · c'est le fichier qui fait l'A/B testing — 8 lignes utiles, connais-les par cœur

events { }

http {
    upstream apps-ab {
        server spring-boot:8080;
        server django:8000;
    }

    server {
        listen 80;

        location /test {
            proxy_pass http://apps-ab/;
        }
    }
}
events { }
Bloc obligatoire dans une conf Nginx, même vide. Il règle la gestion des connexions ; les valeurs par défaut nous vont.
http { }
Le bloc qui contient toute la configuration HTTP.
upstream apps-ab { }
Déclare un groupe de serveurs backend sous un nom que tu choisis. Quand un groupe contient plusieurs serveurs, Nginx alterne entre eux : c'est le round-robin, et c'est ça, ton A/B testing.
server spring-boot:8080;
Un membre du groupe, désigné par son nom de service Docker (résolu par le DNS du réseau ab-network) et son port interne au conteneur.
listen 80;
Nginx écoute sur le port 80, le port HTTP standard — d'où l'URL http://localhost/test sans numéro de port.
location /test { }
« Pour toute requête dont le chemin commence par /test, applique ce qui suit. »
proxy_pass
http://apps-ab/;
Transmets la requête au groupe apps-ab. Le slash final est capital — voir juste en dessous.
Le détail que le prof adore

« Pourquoi le slash à la fin de proxy_pass http://apps-ab/ ? »

Avec le slash : Nginx remplace le morceau capté par le location (/test) par /. Le backend reçoit une requête sur /, sa page d'accueil : ça marche.
Sans le slash : le chemin est transmis tel quel. Spring et Django reçoivent /test, qu'ils ne connaissent pas : 404.

Ton anecdote de debug — sors-la, elle vaut de l'or

« Au début j'avais nommé l'upstream apps_ab avec un underscore, et je me prenais un 400 Bad Request. En cherchant, j'ai compris que Nginx met le nom de l'upstream dans l'en-tête Host de la requête transmise, et que Tomcat — le serveur embarqué dans Spring Boot — applique strictement la RFC, qui interdit l'underscore dans un nom d'hôte. J'ai renommé en apps-ab avec un tiret, et c'est passé. »

Le nginx/Dockerfile qui va avec tient en trois lignes : partir de nginx:alpine, copier ta conf par-dessus celle par défaut (COPY nginx.conf /etc/nginx/nginx.conf), déclarer EXPOSE 80. La consigne demandait un Dockerfile personnalisé plutôt qu'un simple montage de volume : l'image devient autonome, elle embarque sa configuration et se déploie n'importe où.

« Le multi-stage sépare l'environnement de construction de l'environnement d'exécution. Résultat : environ 200 Mo au lieu de 800, et une surface d'attaque réduite puisque les outils de build ne sont pas embarqués en production. »

Le test qu'il va peut-être te faire faire en direct

« Commente EXPOSE 8080, reconstruis, relance. Ça marche encore ? »

Oui, ça marche encore. EXPOSE est purement déclaratif — de la métadonnée pour les humains et les outils. Ce qui rend réellement l'appli joignable, c'est le -p 8080:8080 du docker run, ou la section ports: du compose. Dis-le avant de taper la commande : c'est ça qu'il évalue.

Côté Django, les trois lignes qui comptent

FROM python:3.12-alpine
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
RUN python manage.py makemigrations && python manage.py migrate
EXPOSE 8000
CMD ["python", "manage.py", "runserver", "0.0.0.0:8000"]
COPY requirements.txt
puis RUN pip install
puis COPY . .
L'ordre n'est pas anodin : Docker met chaque instruction en cache. En installant les dépendances avant de copier le code, une simple modification du code ne réinvalide pas l'étape pip install — le rebuild est bien plus rapide.
--no-cache-dir
pip garde normalement une copie des paquets téléchargés. Inutile dans une image qu'on n'installe qu'une fois : on évite de la faire grossir.
runserver 0.0.0.0:8000
Le détail crucial. Sans ça, Django n'écoute que sur 127.0.0.1, c'est-à-dire la boucle locale interne au conteneur — inaccessible depuis l'extérieur, même avec le bon mapping de ports. 0.0.0.0 = « écoute sur toutes les interfaces réseau ».
Sois honnête si on te pousse : manage.py runserver est le serveur de développement de Django. En vraie production on mettrait Gunicorn ou uWSGI. Ici les applis sont volontairement minimales, le sujet du cours c'est la chaîne autour.

Le .dockerignore à côté de chaque Dockerfile joue le même rôle que le .gitignore : il exclut des fichiers du contexte envoyé au démon Docker au moment du build (target/, .git/, caches, fichiers d'IDE). Bénéfice double : build plus rapide, et pas de fichier sensible embarqué par accident dans l'image.

Le piège maison

« Pourquoi PORT et pas WEBSITES_PORT ? »

Le TD 08 le précise noir sur blanc : Azure a changé sa gestion des conteneurs, il faut désormais une variable PORT. Et à défaut de variable, App Service lit l'instruction EXPOSE de l'image pour deviner le port — que tes deux Dockerfile fournissent. C'est cohérent des deux côtés.

6nginx-azure/nginx.conf

Dossier nginx-azure/ · la dernière partie, la plus courte · une seule notion à maîtriser : SNI

Même idée que le Nginx local, mais les backends ne sont plus des conteneurs voisins : ce sont deux URLs publiques Azure, joignables uniquement en HTTPS.

events { }

http {
    upstream apps-ab-azure {
        server app-spring-66045.azurewebsites.net:443;
        server app-django-66045.azurewebsites.net:443;
    }

    server {
        listen 80;

        location /test {
            proxy_pass https://apps-ab-azure/;
            proxy_ssl_server_name on;
            proxy_ssl_name $proxy_host;
        }
    }
}
…azurewebsites.net:443
Port 443 = HTTPS. Un App Service ne répond pas en HTTP non chiffré.
proxy_pass https://…
https et non http : Nginx doit établir une connexion chiffrée sortante.
proxy_ssl_server_name on;
Active SNI sur cette connexion sortante. Sans ça, la connexion échoue.
proxy_ssl_name $proxy_host;
Le nom de domaine à annoncer dans le SNI, repris dynamiquement du serveur choisi.
Explique SNI comme ça

« SNI, Server Name Indication, c'est l'extension TLS qui permet au client d'annoncer quel domaine il veut joindre dès le début du handshake, avant que le certificat soit choisi. Azure App Service héberge des milliers d'applications derrière les mêmes adresses IP : sans SNI, il ne sait pas quel certificat présenter ni vers quelle application router, et la connexion échoue. »

Si on creuse — réponds honnêtement, ça paie

« Et l'en-tête Host ? »

C'est la limite connue de cette configuration : quand un upstream contient plusieurs serveurs, l'en-tête Host transmis vaut par défaut le nom de l'upstream, qu'Azure ne reconnaît pas comme une de ses applis. « En local le round-robin fonctionne pleinement ; pour une vraie production sur Azure, je gérerais le Host par backend, avec un map et un split_clients — ou j'utiliserais Azure Front Door, le service natif pour ce type de routage, que la consigne mentionne d'ailleurs. » Ne prétends pas que c'est parfait : reconnaître une limite en sachant comment la lever vaut mieux que bluffer.

Échelle 5 — le jour J

Ce qu'on va te demander de faire, pas juste de dire

La défense n'est pas un oral de récitation : le prof ouvre ton dépôt, pointe une ligne, et te demande souvent de modifier quelque chose en direct. Voici les gestes types.

1 · Changer un port

Trois fichiers, toujours les mêmes : le Dockerfile de l'appli (CMD + EXPOSE), le docker-compose.yml (ports:), le nginx/nginx.conf (la ligne server …:port; de l'upstream). Puis docker compose up --build et tu testes /test.

2 · Commenter EXPOSE et prouver que ça marche encore

Annonce le résultat avant de lancer : « ça va continuer de fonctionner, parce qu'EXPOSE ne fait que documenter ». Puis rebuild, relance, montre.

3 · Enlever depends_on et expliquer ce que ça change

Les services démarrent en parallèle ; Nginx peut se lancer avant les applis et échouer sur ses premières requêtes. Ça ne rend pas le projet cassé, ça le rend imprévisible.

4 · Ajouter une variable ou une condition au pipeline

Deux formes à savoir écrire : un bloc variables: en haut du fichier (ou dans un job), et une règle rules: - if: '$CI_COMMIT_BRANCH == "main"' pour qu'un job ne tourne que sur certaines branches. Même logique avec $CI_COMMIT_TAG pour ne réagir qu'aux tags.

5 · Renommer les images (par exemple ajouter un suffixe)

Le nom d'une image apparaît là où on la construit et là où on l'utilise : dans le .gitlab-ci.yml (docker build -t et docker push, les deux doivent rester identiques) et dans terraform/variables.tf (spring_image, django_image). Change les deux côtés ou l'App Service cherchera une image qui n'existe pas.

Le vocabulaire minimum vital

image
Un modèle figé, en lecture seule, qui contient une appli et tout ce qu'il lui faut pour tourner.
conteneur
Une instance en cours d'exécution d'une image. Une image, plusieurs conteneurs possibles.
registre (registry)
Le dépôt où l'on stocke et partage des images. Docker Hub en public, ton ACR en privé.
reverse proxy
Un serveur placé devant d'autres serveurs : il reçoit les requêtes des clients et les redistribue. Ici, Nginx.
round-robin
Répartition à tour de rôle, chacun son tour, sans mémoire.
CI / CD
Intégration continue (on compile et teste automatiquement à chaque modification) / livraison continue (on déploie automatiquement dans la foulée).
runner
Le programme qui exécute réellement les jobs du pipeline. Chez toi : un conteneur Docker sur ta machine.
Infrastructure as Code
Décrire ses serveurs dans des fichiers versionnés plutôt que de cliquer dans une interface.
idempotent
Se dit d'une opération qu'on peut relancer sans changer le résultat. terraform apply deux fois de suite : la deuxième ne fait rien.

Si le prof voit du rouge dans tes pipelines

Ça peut arriver, et ce n'est pas grave si tu sais dire pourquoi. Un job GitLab qui reste en Pending avec la mention stuck ne signifie pas que ton code est cassé : ça veut dire qu'aucun runner n'est en ligne pour le prendre. Et ton runner, c'est un conteneur Docker sur ta machine — s'il n'est pas démarré, personne n'exécute rien.

La réponse, si la question tombe

« Ce job est en attente, pas en échec : mon runner est un conteneur Docker enregistré sur ma machine, et il n'était pas démarré. Dès qu'il repasse en ligne, GitLab lui redonne le job. Le pipeline vert sur le tag nginx-azure est passé sur ce même commit. »

Les trois réflexes d'oral

  1. Ne mens jamais sur ce que tu n'as pas fait. « Je ne l'ai pas mis en place, mais voilà comment je m'y prendrais » vaut infiniment mieux qu'une invention qu'il vérifiera en trente secondes.
  2. Si tu bloques, raisonne à voix haute. « Je ne suis pas certain, mais d'instinct je dirais X, parce que Y. » Tu montres une méthode plutôt qu'un trou.
  3. Explique ce que tu tapes pendant que tu le tapes. Le silence pendant une manipulation est le pire moment de la défense ; le commentaire à voix haute prouve que tu sais où tu vas.
